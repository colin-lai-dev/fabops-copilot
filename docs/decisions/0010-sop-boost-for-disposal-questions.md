# ADR-0010: 處置類問題在檢索排序中提高 SOP 權重

- 日期：2026-11-10
- 狀態：已採用

## 背景

人工標註（50 題，Colin）發現 25 題 open（「剛跳某 alarm，我該怎麼處理？」）中，有 19 題的回答是異常報告裡的摘要句
（「依 SOP 處置：確認異常後等待重測……」），沒有給出 SOP 的具體步驟。

量化（dev＋校準題庫的 open 題，n=25，不用 test）：

- 文件層：應引用的 SOP 在前 5 名的比例（Recall@5）是 25/25，問題**不在找不到 SOP**。
- 切塊層：送進 LLM 的 8 個 chunk 中，SOP 的「4. 處置步驟」那一塊只有 13/25 題在裡面；
  其餘位置被異常報告占走（8 個 chunk 中 SOP 只占 85/200）。異常報告整份是一個 chunk，字面上和問題重疊很多。

## 選項

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| A. 處置類問題把 SOP chunk 的 RRF 分數乘上固定權重 | 一行邏輯、只動排序；權重 1.2 就讓處置步驟 25/25 進入 context | 要靠關鍵詞判斷問題類型；其他廠區／其他 alarm 的 SOP 章節也會被往前推 |
| B. SOP 與異常報告各取固定名額再合併（例如 SOP 6 + 報告 2） | 保留一些異常報告的脈絡 | 名額 6 時處置步驟只有 23/25 進入 context，比 A 差 |
| C. 檢索到 SOP 就把整份 SOP 的章節都帶進 context（引用展開） | 步驟與升級條件一定齊全 | 要改 context 組裝與 token 預算，Phase 1 已決定不做引用展開（open-questions） |
| D. 不改，留給 Phase 2 agent | 不動 Phase 1 系統 | 主力系統在最常見的問法上答不出步驟 |

## 決定

選擇 A。`RetrievalConfig.sop_boost = 1.2`；`is_disposal_query()`（「怎麼處理」「如何處置」「處置步驟」等關鍵詞）成立時，
SOP chunk 的融合分數乘以 1.2，再取前 k 個 chunk。只有預設系統（`hybrid-bm25` preset）開啟，
`rag-dense` 等 baseline 維持 1.0，讓歷史數字可以比較。`-sopW` 後綴可以在 eval 中改權重（`-sop1` 為關閉）。

## 理由

- 1.2 是測過的權重（1.2／1.5／2）中最小、且讓處置步驟 25/25 進入 context 的值；名額法（B）最好只有 23/25。
- 端到端（qwen3:8b）：open 題的要點命中率，校準題庫 0.155 → 0.591（n=110 點）、dev 0 → 0.600（n=15 點）；
  dev 其他題型沒有任何一題的回答、引用或 Recall@5 改變（n=69／65），MRR 0.729 → 0.758。
  要點命中率用 `evals/rubric_match.py` 計算，它在標註當下的輸出上和 Colin 的標註 125/125 點一致。
  細節見 `docs/experiments.md` 2026-11-10。
- 只讀問題文字、在權限 pre-filter 之後作用，不影響 ADR-0001／0003：被往前推的只會是這位使用者本來就看得到的 SOP。

## 後果

- 嚴格通過率仍是 0：第 5 點「升級條件」在兩個版本都是 0/22（升級條件是另一個章節，boost 後只有 13/25 題進入 context，
  而且即使在 context 裡 qwen3 也沒有寫出來）。這類「要把同一份 SOP 的多個章節湊齊」的問題留給 Phase 2（引用展開或 agent 查詢 SOP 全文）。
- 數值判讀錯誤（把超標判成未超標）boost 前後各 1 題，屬於模型能力，不是檢索問題；Haiku 5.5 上再觀察。
- 問題類型靠關鍵詞判斷；若之後的問法不含這些詞（例如「CHC 剛跳 EPD timeout，下一步？」），boost 不會啟動。
  Phase 2 可改由 agent 的路由決定，或擴充關鍵詞並在 dev 上重新確認。
- 以 rerank、切塊或 context 數量重新調參時，要連同 `sop_boost` 一起重測。
